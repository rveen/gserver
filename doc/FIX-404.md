# Not-found handling: three faults and their fixes

Three defects in how gserver answers a request for something that is not there.
The first two compound, and together they produced a report that pointed
nowhere near either of them:

```
Failed to load module script: Expected a JavaScript-or-Wasm module script but
the server responded with a MIME type of "text/html". Strict MIME type checking
is enforced for module scripts per HTML spec.
```

Nothing was wrong with the MIME type. The server was sending an HTML document
because it had decided to serve a different file than the one asked for, and
labelled it correctly.

The fix touches two repositories:

| Repository | File | Change |
|---|---|---|
| `rveen/golib` | `fn/get.go` | A missing file no longer falls back to the directory index |
| `rveen/golib` | `fn/sys.go` | New `FNode.IsDir`; `index()` ranks its candidates |
| `rveen/gserver` | `dynhandler.go` | Directory URLs redirect to a trailing slash |
| `rveen/gserver` | `request.go` | A directory without an `index.*` is listed, not 500'd |

---

## Fault 1 — a missing file was answered with the directory's index, under a 200

### What happened

`fn.get` resolves a URL one path element at a time. When an element does not
exist, it lands in `case ""` (`fn/get.go`), which backs up to the parent
directory and tries two recoveries: a `_wildcard` entry, then the directory's
`index.*` file.

That second recovery ran regardless of what the element looked like. So a
request for a file that was not there was answered with the directory's index
page — **HTTP 200**, `Content-Type: text/html`:

```
GET /app/bundle.js    200  text/javascript    (the file exists)
GET /app/missing.js   200  text/html          (body: app/index.html)
GET /app/nope.css     200  text/html          (body: app/index.html)
GET /app/sub/deep.js  404  text/plain         (that directory has no index)
```

The trigger is precise: **a file that does not exist, in a directory that
contains an `index.*` or `readme.*`**. A directory without one already 404'd,
which is why this could sit unnoticed — it depended on the shape of the tree.

### Why it mattered more than a wrong header

A browser fetching a module script rejects an HTML response on MIME grounds,
which is the error above. But the MIME check was the only thing that noticed.
Everywhere else the wrong answer was silent:

- A stylesheet at a stale path returned HTML with a 200. The browser discarded
  it and the page rendered unstyled, with no failed request to find.
- An image, a font, a source map: 200, wrong bytes, no error.
- **Every 404 in the application was invisible.** Monitoring, logs and anything
  counting error rates saw success.

A wrong response under a 200 is worse than a 404, because a 404 is a fact
somebody can act on.

### The fix

`fn/get.go:125` — before falling back to the index, ask whether the path element
was naming a file:

```go
if namesAFile(part) {
    return errors.New("404")
}
if !fn.index() {
    return errors.New("404")
}
```

`info()` has already established the file is not there; the fallback is for a
path *continuing into a document*, not for a file request.

### The line between the two, and why it is not "contains a dot"

`namesAFile` (`fn/get.go:193`) keys on a filename extension **containing at
least one letter**:

```go
func namesAFile(part string) bool {
	ext := filepath.Ext(part)
	if len(ext) < 2 {
		return false
	}
	for _, r := range ext[1:] {
		if unicode.IsLetter(r) {
			return true
		}
	}
	return false
}
```

A plain dot test would have been wrong. `filepath.Ext("1.2")` is `".2"`, so
`docs/1.2` — a section number, a legitimate document part — would have become a
404. Same for `docs/v0.98`. Requiring a letter keeps those working while
catching `.js`, `.css`, `.wasm`, `.map` and the rest.

The index fallback itself is untouched. It is a real feature: `docs/cap1`
still resolves to a section of `docs/index.md`, which is what it is for.

## Fault 2 — a URL naming a directory was served without a redirect

### What happened

`/app` and `/app/` both returned `app/index.html` with a 200. No redirect.

That is not a cosmetic difference. A browser given `/app` resolves every
relative reference in the returned page against `/`, not against `/app/`. So
`<script type="module" src="bundle.js">` becomes a request for **`/bundle.js`**
— a different file, or none.

Two things made this hard to see. `.html` is not in `TplExtensions`
(`request.go`), so `index.html` is never template-processed and never receives
the `<base href="$R.urlbase">` that would otherwise paper over it. And fault 1
then answered the wrong request with a 200 and an HTML body.

The full chain, reproduced against a tree with an `index.html` at the root and
the application in `/app`:

```
GET /app          200  text/html    serves app/index.html
GET /bundle.js    200  text/html    fault 1: serves the root index.html
```

Which the browser reports as a MIME error about a module script — three steps
from the actual mistake, which was a URL missing a slash.

### The fix

`dynhandler.go:146` — `redirectToDirectory`, called at `dynhandler.go:78`. A URL
that literally names a directory gets a **301** to the same URL with a trailing
slash. This is what `http.FileServer` does, for this reason.

Three details are deliberate:

**It runs after the authentication check.** Otherwise the difference between a
301 and a login redirect would tell an anonymous caller whether a protected
directory exists.

**GET and HEAD only.** A 301 permits a client to reissue a POST as a GET, which
would drop the form body. gserver's templates gate writes on `R.method`, so that
would quietly turn a submission into a read.

**The probe path and the redirect target are different strings.** The probe uses
`r.Path`, which is hostname-prefixed in multi-host mode; the target uses
`rh.URL.Path`. Swapping them would send clients to a URL with the hostname in
it. Note also that `ConvertRequest` runs `filepath.Clean`, which strips the
trailing slash — so `rh.URL.Path` is the only place that information survives.

### `FNode.IsDir` resolves nothing, on purpose

`fn/sys.go` gains `IsDir`, which answers only *is there a directory at exactly
this path*: no extension guessing, no index lookup, no `_wildcard` matching, no
continuing into a document.

That restraint is the point. A redirect built on `Get`'s resolution would fire
for URLs that merely resemble directories — a `_user` wildcard would send
`/user/rolf` to a URL exposing the wildcard, which does not resolve. Because
`IsDir` is literal, `/doc` (which resolves to `doc.md` by guessing an extension)
and `/doc/cap1` (a document part) are both left alone.

It does not modify its receiver, so it is safe on the root `FNode` that handlers
share across requests.

## Fault 3 — a directory without an `index.*` was answered with a 500

### What happened

A directory with no `index.*` resolves to itself: `fn.get` leaves the node at
type `dir`, with the entry list in `fn.Data` and `fn.Content` empty. That is the
correct shape — the listing is the content — but nothing downstream would render
it unless the site happened to configure a `dir` template:

```
GET /plain/      500  text/plain    (body: "Empty content")
GET /plain/sub/  500  text/plain    (an empty directory, likewise)
```

`request.go` looked the type up in `srv.Templates`, logged `no template for type
dir`, and called `Process` on the nil template. `ogdl`'s `Process` is nil-safe,
so it returned an empty byte slice rather than panicking, and `dynhandler.go`
turned that into `http.Error(w, "Empty content", 500)`.

Three separate things were wrong with that:

- The 500 blamed the request for a server configuration gap.
- `len(content) == 0` is not evidence of failure. **A zero-byte file — an empty
  `.txt`, a placeholder `.js` — got the same 500.**
- A missing `document` or `data` template hit the identical branch, so a real
  configuration fault and an empty file were indistinguishable in the response
  *and* in the log.

### The fix

Two halves, in `request.go` and `dynhandler.go`.

`Process` now returns an error instead of silently emitting nothing, and the
`dir` case has a fallback:

```go
tpl := srv.Templates[tp]
if tpl == nil {
    if r.File.Type == "dir" {
        r.File.Content = dirListing(r)
        r.Mime = "text/html"
        return nil
    }
    return fmt.Errorf("no template configured for type %q", tp)
}
```

`dirListing` (`request.go`) renders a plain HTML index from `fn.Data`. **A
configured `dir` template always wins** — the built-in listing exists only so
that "no `index.*`" never means "no answer". Sites with a `dir` template see no
change at all.

`dynhandler.go` propagates the error and drops the length test:

```go
if err := r.Process(srv); err != nil {
    log.Printf("DynHandler %s: %v\n", rh.URL.Path, err)
    http.Error(w, http.StatusText(500), 500)
    return
}
...
http.ServeContent(w, rh, filepath.Base(r.Path), time.Time{}, bytes.NewReader(r.File.Content))
```

An empty body is now a legitimate 200. A missing `document` template is still a
500, but one that says which template is missing.

### Why this fault and fault 2 are the same fault

The built-in listing links every entry relatively — `<a href="a.txt">`, not
`<a href="/plain/a.txt">` — because it has no reliable prefix to build from in
multi-host mode. **That is correct only at a URL ending in a slash.** Served at
`/plain`, every link in the listing points at the root.

So the trailing-slash redirect is not a nicety for listings, it is what makes
them work at all. The two fixes have to ship together.

Two details in `dirListing` follow from the same reasoning:

- **Entries beginning with `_` are omitted.** Those are gserver's path variables
  (`/_user` matches any element); they are not followable URLs, so linking them
  would only produce dead entries. Dot entries are already dropped upstream by
  `fn.dir`.
- **Names are escaped** with `html.EscapeString`. A filename is attacker-
  controlled on any tree that accepts uploads, and `<img src=x onerror=...>.txt`
  is a legal filename on every filesystem gserver runs on.

### A directory is no longer read as a file

`fn/get.go`, final `case "dir"`, previously ran unconditionally:

```go
fn.index()
fn.processFile(raw, noRead)
```

With no index, `processFile` called `os.ReadFile` on a *directory*. The error
was discarded — `get` returns `dir()`'s error, not `processFile`'s — so this was
invisible, but it was a wasted syscall on every listing. It is now guarded:

```go
if err == nil && fn.index() {
    fn.processFile(raw, noRead)
}
```

## A fourth thing, found on the way: `index.*` picked the wrong file

`fn.index()` took the **first** directory entry with an `index.` or `readme.`
prefix, in readdir order — which is alphabetical. A directory holding both
`index.css` and `index.html` therefore served the stylesheet:

```
GET /multi/     200  text/css     (body: index.css)
```

This is fault 1's failure mode arriving by a different road: a 200 carrying
content of a type the caller cannot use. It is also the case a browser reports
as a MIME error, so it would have been misdiagnosed the same way.

`index()` now ranks candidates instead of taking the first (`fn/sys.go`):

```go
var indexExts = []string{".html", ".htm", ".md", ".ogdl", ".txt"}
```

`index.*` outranks `readme.*`; within each, the order above applies; an
unlisted extension still qualifies, last, so a directory whose only candidate
is `index.json` keeps resolving exactly as before. Nothing that resolved before
stops resolving — only the choice between several candidates changes.

While there: `index()` no longer logs `requesting fn.index with empty data`. An
empty directory is a normal thing to ask about, and after this change it is a
directory listing rather than an error, so it was logging once per request.

## Behaviour changes

Everything below is a deliberate change in what the server returns. Read this
part before deploying.

### 1. A missing file with an extension now returns 404 instead of 200 + index

```
                        before                    after
GET /app/missing.js     200  text/html            404  text/plain
GET /app/nope.css       200  text/html            404  text/plain
GET /app/sheaf.wasm     200  text/html            404  text/plain
```

**This will surface 404s that were previously invisible.** If anything in a
served tree has been requesting a path that does not exist, it has been getting
a 200 and an HTML body, and now gets a 404. Expect error rates to rise on first
deploy — that is the fault becoming visible, not a new one appearing.

**What could break.** Any page or client that depended on a missing
extension-bearing path returning the directory index. Such a dependency is
almost certainly accidental, but it is a real change and `fn` may have consumers
beyond gserver.

**What does not change:**

- Files that exist: unchanged.
- Directories: still resolve to their `index.*`.
- `docs/cap1` and other extension-less path continuations: unchanged.
- `docs/1.2`, `docs/v0.98`: unchanged, by the letter rule above.
- A missing file in a directory with no index: already 404, still 404.

### 2. Directory URLs now redirect

```
                        before                    after
GET /app                200  text/html            301  ->  /app/
GET /app/               200  text/html            200  text/html
POST /app               200                       200  (unchanged)
GET /prot (protected)   302  ->  /login           302  ->  /login  (unchanged)
```

The query string is preserved: `/app?m=raw` → `/app/?m=raw`.

**What could break.** A client that hardcodes a directory URL without a trailing
slash and does not follow redirects will now see a 301 where it saw a 200.
Browsers and `curl -L` follow it; a bare `curl`, or a script using a minimal
HTTP client, will not.

**301 is cached permanently by browsers.** This matches `http.FileServer` and is
what clients expect, but it is sticky: if a path that is a directory today
becomes a file later, clients that saw the 301 keep appending the slash. If that
is a concern for a server whose content changes shape, `308` behaves identically
for GET without the permanence — a one-word change in `redirectToDirectory`.

### 3. A directory without an `index.*` is listed instead of 500'ing

```
                        before                    after
GET /plain/             500  "Empty content"      200  text/html   (listing)
GET /plain/sub/         500  "Empty content"      200  text/html   (empty listing)
GET /plain/empty.txt    500  "Empty content"      200  text/plain  (empty body)
GET /docs/  (no tpl)    500  "Empty content"      500  (log names the template)
```

**A configured `dir` template always wins.** A site that has one sees no change.

**What could break.** A tree served without a `dir` template now exposes its file
names at directory URLs where it previously returned a 500. On most trees that
is the intent; if some directory was relying on the 500 to stay opaque, give it
an `index.*` or list it under `protected` in `.conf/config.ogdl`. Entries
starting with `_` or `.` are never listed.

### 4. A directory with several `index.*` files picks a different one

```
                        before                    after
GET /multi/             200  text/css             200  text/html
   (index.css + index.html)
```

Only directories holding **more than one** `index.*`/`readme.*` candidate are
affected. A single candidate resolves exactly as before, whatever its extension.

### 5. Not covered

Two paths were left alone deliberately, and neither gets the redirect:

- **`DynamicHandlerFn`** (the deprecated `fs != nil` branch) has its own
  fallback logic and skips `checkPath` entirely. It is retained for
  `github.com/trukeio/gserver`; changing a deprecated path was not worth the
  risk. It *does* get fault 1's fix, since that lives in `fn`.
- **`StaticFileHandler`** (`/static/*`, `/file/*`) serves assets, where the
  relative-URL problem does not arise. Easy to add if the consistency is wanted.

- protected directory → login, not a 301
- missing asset → 404

- a `_user` directory is omitted from the listing
- a zero-byte file → 200 with an empty body, not a 500

Both suites were confirmed to fail when the corresponding fix is removed.

## Reproducing

```bash
mkdir -p /tmp/webroot/.conf /tmp/webroot/app
printf 'host localhost\n\nhttp\n  port 8080\n' > /tmp/webroot/.conf/config.ogdl
printf 'title "repro"\n'                       > /tmp/webroot/.conf/context.ogdl
printf '<!doctype html><h1>site</h1>\n'        > /tmp/webroot/index.html
printf '<!doctype html><script type="module" src="bundle.js"></script>\n' \
                                               > /tmp/webroot/app/index.html
printf 'export const answer = 42;\n'           > /tmp/webroot/app/bundle.js

cd /files/go/src/github.com/rveen/gserver && go build -o /tmp/gserver ./gserver
cd /tmp/webroot && /tmp/gserver -H :8080
```

Then, in another shell:

```bash
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' localhost:8080/app/missing.js
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' localhost:8080/app
mkdir -p /tmp/webroot/plain && printf 'a\n' > /tmp/webroot/plain/a.txt
curl -s localhost:8080/plain/
```

Before: `200 text/html`; `200` with no redirect; `500 Empty content`.
After: `404 text/plain`; `301 http://localhost:8080/app/`; an HTML listing.
